This page walks through the moving parts behind [CoCart AI](/ai-agents): how an agent gets a token, what happens at checkout, and how the approval flow protects the customer.

## Agent discovery

Everything starts with a manifest — a public, unauthenticated endpoint an agent can fetch to learn what a store supports.

<Note>
  `GET /wp-json/cocart/ai/v1/agent/manifest` — public, no authentication required.
</Note>

```json Manifest response
{
  "store": "My Store",
  "url": "https://my-store.com",
  "currency": "GBP",
  "currency_symbol": "£",
  "capabilities": {
    "catalog": true,
    "cart": true,
    "checkout": true,
    "agent_tokens": true
  },
  "endpoints": {
    "products": "/wp-json/cocart/v2/products",
    "add_to_cart": "/wp-json/cocart/v2/cart/add-item",
    "cart": "/wp-json/cocart/v2/cart",
    "token_issue": "/wp-json/cocart/ai/v1/agent/token",
    "approve": "/wp-json/cocart/ai/v1/agent/approve/{key}",
    "reject": "/wp-json/cocart/ai/v1/agent/reject/{key}"
  },
  "token_scopes_available": ["cart:read", "cart:write", "checkout:read", "checkout:execute"],
  "spend_limits_supported": true,
  "approval_flow_supported": true
}
```

<ResponseField name="capabilities" type="object">
  Which store features are enabled.
  <Expandable title="capabilities properties">
    <ResponseField name="catalog" type="boolean">Whether product browsing is available.</ResponseField>
    <ResponseField name="cart" type="boolean">Whether cart operations are available.</ResponseField>
    <ResponseField name="checkout" type="boolean">Whether checkout is available.</ResponseField>
    <ResponseField name="agent_tokens" type="boolean">Whether this store issues agent tokens at all.</ResponseField>
  </Expandable>
</ResponseField>

<ResponseField name="token_scopes_available" type="string[]">
  The full set of scopes a customer can grant when issuing a token. See [Token scopes](#token-scopes) below.
</ResponseField>

<ResponseField name="mcp_tools" type="array">
  Only present on WordPress 7.0+ with the <Tooltip tip="A WordPress 7.0+ standard for registering typed, permission-checked actions AI agents and other tools can call">Abilities API</Tooltip> active — the <Tooltip tip="Model Context Protocol — a standard way for AI clients like Claude to discover and call tools">MCP</Tooltip> tool definitions an agent can call directly, reachable from Claude Code, Claude Desktop, or any MCP-connected client.
</ResponseField>

## Registering an agent

Before any customer can issue a token, a store admin registers the agent itself. Registration is a one-time setup step per agent, not per customer.

<Note>
  `POST /wp-json/cocart/ai/v1/agent/register` — requires the `manage_woocommerce` capability.
</Note>

<ParamField body="agent_id" type="string" required>
  Unique slug for the agent, e.g. `my-shopping-bot`.
</ParamField>
<ParamField body="agent_name" type="string" required>
  Human-readable name shown in emails and admin.
</ParamField>
<ParamField body="allowed_scopes" type="string[]" required>
  Scopes users may grant this agent when issuing a token.
</ParamField>
<ParamField body="webhook_url" type="string">
  URL to POST lifecycle events to.
</ParamField>
<ParamField body="default_checkout_mode" type="string" default="payment_token">
  `payment_token` or `approval_only`.
</ParamField>
<ParamField body="require_identity_verification" type="boolean" default="true">
  Require email verification before token activation.
</ParamField>

## Issuing a token

A logged-in customer — never the agent itself — issues a scoped token for a registered agent. The plain token (`act_...`) is returned exactly once; only its SHA-256 hash is stored, so it can never be recovered from the database afterward.

<Note>
  `POST /wp-json/cocart/ai/v1/agent/token` — requires an authenticated WordPress user.
</Note>

<ParamField body="agent_id" type="string" required>
  Must match a registered agent.
</ParamField>
<ParamField body="scope" type="string[]" required>
  Subset of the agent's `allowed_scopes`.
</ParamField>
<ParamField body="max_spend" type="number">
  Maximum spend in `currency`. Omit for no limit.
</ParamField>
<ParamField body="expires_in" type="integer" default="3600">
  Seconds until expiry. Maximum 86400 (24 hours).
</ParamField>
<ParamField body="requires_approval" type="boolean" default="true">
  Require approval before checkout.
</ParamField>
<ParamField body="approval_threshold" type="number">
  Only require approval when the order total is at or above this amount.
</ParamField>
<ParamField body="checkout_mode" type="string">
  `payment_token` or `approval_only`.
</ParamField>
<ParamField body="wc_payment_token_id" type="integer">
  Required when `checkout_mode` is `payment_token`. Must belong to the authenticated user.
</ParamField>
<ParamField body="identity_email" type="string">
  Required when the agent has `require_identity_verification: true`. Must match the user's WordPress or WooCommerce billing email.
</ParamField>

<Tabs>
  <Tab title="Identity verification required">
    <Steps>
      <Step title="Token created as pending_identity">
        The `202 Accepted` response tells the agent to wait: `{ "status": "pending_identity" }`.
      </Step>
      <Step title="Verification email sent">
        A 15-minute signed link goes to the customer's email.
      </Step>
      <Step title="Customer clicks the link">
        `GET /agent/verify-identity/{key}` confirms the request.
      </Step>
      <Step title="Token activates">
        Status flips to `active`, and a `token_activated` webhook fires to the agent.
        <Check>While pending, the token can still browse and add to cart — only checkout is blocked.</Check>
      </Step>
    </Steps>
  </Tab>
  <Tab title="No verification required">
    <Steps>
      <Step title="Token created as active">
        The `201 Created` response returns the plain token immediately — no email round-trip needed.
      </Step>
    </Steps>
  </Tab>
</Tabs>

<ResponseField name="token" type="string">
  The plain `act_` token — shown once, never stored.
</ResponseField>
<ResponseField name="checkout_mode" type="string">
  Echoes back `payment_token` or `approval_only` for this token.
</ResponseField>
<ResponseField name="payment_method_label" type="string">
  Resolved at response time (e.g. "Visa ending 4242") and never stored — filtered by gateway integrations.
</ResponseField>
<ResponseField name="spent_total" type="number">
  Running total deducted as orders are approved. Starts at `0`.
</ResponseField>
<ResponseField name="expires_at" type="string">
  ISO 8601 expiry timestamp.
</ResponseField>

## Checkout interception

The agent shops using CoCart's normal cart endpoints with `Authorization: Bearer act_...`. The interesting part happens at checkout — CoCart AI intercepts `POST /cocart/v2/checkout` before CoCart's own logic runs.

<Steps>
  <Step title="Token is valid">
    Active, not expired, not revoked. <Badge color="red">401 invalid_agent_token</Badge> otherwise.
  </Step>
  <Step title="Not pending identity">
    <Badge color="red">403 agent_token_pending_identity</Badge> if the customer hasn't verified yet.
  </Step>
  <Step title="Has checkout:execute scope">
    <Badge color="red">403 insufficient_scope</Badge> otherwise.
  </Step>
  <Step title="Passes extension scope gates">
    E.g. `subscription:execute` when the cart contains a subscription product.
  </Step>
  <Step title="Stays within max_spend">
    <Badge color="red">402 spend_limit_exceeded</Badge> if the order would exceed the token's limit.
  </Step>
  <Step title="Decide: approval needed?">
    <Tabs>
      <Tab title="Total ≥ approval_threshold">
        Cart snapshot saved, pending order created, approval email sent.
        <Check>Returns `202 Accepted` — nothing is placed yet.</Check>
      </Tab>
      <Tab title="Below threshold">
        Checkout proceeds immediately.
        <Check>Returns `200 OK` with order details.</Check>
      </Tab>
    </Tabs>
  </Step>
</Steps>

Any failed check returns immediately with a specific error — an expired token, insufficient scope, or a spend limit that would be exceeded never reaches the point of creating a pending order.

## The approval flow

When an order needs approval, the customer gets an email with one-click Approve/Reject links (and CoCart AI can use WordPress 7.0's AI Client to summarize the cart in plain English rather than a raw items table).

<Tabs>
  <Tab title="payment_token mode">
    The agent uses a saved WooCommerce payment method (e.g. a Stripe card on file). On approval, CoCart AI creates the order and charges the card without the customer visiting checkout.

    <Steps>
      <Step title="Customer clicks Approve">
        `POST /agent/approve/{key}`
      </Step>
      <Step title="Order created, payment charged">
        The saved payment token is re-validated (cards can be deleted between issuance and approval) and charged via the gateway.
      </Step>
      <Step title="Success or failure">
        <CodeGroup>
          ```json Success — 200 OK
          {
            "order_id": 1047,
            "order_url": "https://my-store.com/my-account/orders/1047"
          }
          ```
          ```json Failure — 402 Payment Required
          {
            "code": "payment_failed",
            "message": "The saved payment method could not be charged.",
            "data": { "status": 402 }
          }
          ```
        </CodeGroup>
        On failure, the pending order is marked `payment_failed`, the customer is notified, and `cocart_agent_payment_failed` fires.
      </Step>
    </Steps>

    <Note>Requires `wc_payment_token_id` at token issuance, and a gateway that supports server-side charging via a saved token.</Note>
  </Tab>
  <Tab title="approval_only mode">
    No saved payment method is needed. On approval, CoCart AI hands the customer a pre-filled checkout link to complete payment themselves.

    <Steps>
      <Step title="Customer clicks Approve">
        `POST /agent/approve/{key}`
      </Step>
      <Step title="Redirect generated">
        ```json 200 OK
        {
          "redirect_url": "https://my-store.com/checkout?cart_key=xxx"
        }
        ```
      </Step>
    </Steps>

    <Note>No payment is processed by CoCart AI — it only coordinates cart state. Works with any gateway, and suits guests or customers who prefer to handle payment themselves.</Note>
  </Tab>
</Tabs>

Rejecting is the same shape in both modes: `POST /agent/reject/{key}` marks the pending order `rejected`, fires `cocart_agent_order_rejected`, and notifies any registered webhooks with `200 OK { "status": "rejected" }`.

## Spend tracking

Every approved order deducts its total from the token's running `spent_total`.

<Check>
  If a pending order would push spending past `max_spend`, checkout is blocked with a spend-limit error **before** any approval email goes out — a customer never gets asked to approve something already destined to fail on spend grounds.
</Check>

## Webhooks

Agents (and integrations like Zapier) can be notified of lifecycle events via outbound webhooks, delivered asynchronously with automatic retries when Action Scheduler is available.

<AccordionGroup>
  <Accordion title="token_activated" icon="key">
    Fires when a customer completes identity verification and the token moves to `active`.
  </Accordion>
  <Accordion title="order.approved" icon="check">
    Fires when a pending order is approved and payment succeeds (or handed off to the customer in `approval_only` mode).
  </Accordion>
  <Accordion title="order.rejected" icon="xmark">
    Fires when a customer rejects a pending order.
  </Accordion>
  <Accordion title="payment.failed" icon="triangle-exclamation">
    Fires when payment processing fails after an order was approved.
  </Accordion>
</AccordionGroup>

## Token scopes

<AccordionGroup>
  <Accordion title="cart:read" icon="eye">
    Read current cart contents and totals.
  </Accordion>
  <Accordion title="cart:write" icon="pen">
    Add, update, and remove cart items.
  </Accordion>
  <Accordion title="cart:gift_card" icon="gift">
    Apply gift card codes to the cart (requires WooCommerce Gift Cards).
  </Accordion>
  <Accordion title="checkout:read" icon="eye">
    Read checkout data.
  </Accordion>
  <Accordion title="checkout:execute" icon="bolt">
    Trigger checkout, subject to the approval flow above.
  </Accordion>
  <Accordion title="subscription:execute" icon="rotate">
    Place orders containing subscription products (requires WooCommerce Subscriptions).
  </Accordion>
</AccordionGroup>

<Tip>
  Integration plugins can add further scopes via a filter — [contact support](mailto:support@cocartapi.com) if you have a use case that needs a custom one.
</Tip>

## Error responses

All errors follow the standard WordPress REST API shape: `{ "code", "message", "data": { "status" } }`.

<Accordion title="Full error code reference">
  | Code | HTTP | Description |
  |---|---|---|
  | `invalid_agent_token` | 401 | Token missing, malformed, expired, or revoked |
  | `insufficient_scope` | 403 | Token lacks the required scope for this operation |
  | `agent_token_pending_identity` | 403 | Token awaiting email identity verification |
  | `spend_limit_exceeded` | 402 | Order would exceed the token's `max_spend` |
  | `no_payment_token` | 422 | No saved payment method associated with token |
  | `invalid_payment_token` | 422 | Saved payment method is invalid or was deleted |
  | `subscription_scope_required` | 403 | Cart contains a subscription; token needs `subscription:execute` |
  | `identity_email_mismatch` | 422 | `identity_email` does not match the user's account |
  | `invalid_verify_key` | 410 | Verification link is invalid or has expired |
</Accordion>

## Extensibility

<AccordionGroup>
  <Accordion title="Custom scopes" icon="key">
    Store-specific or third-party plugins can register additional scopes (like `subscription:execute` or `cart:gift_card`) and gate checkout on them.
  </Accordion>
  <Accordion title="Custom checkout gates" icon="shield-halved">
    Block checkout on arbitrary conditions beyond scope — e.g. requiring a scope only when the cart contains a specific product type.
  </Accordion>
  <Accordion title="Payment method labels" icon="credit-card">
    Gateways can supply richer, human-readable labels (e.g. "Visa ending 4242") shown in tokens and approval emails.
  </Accordion>
  <Accordion title="Order summary lines" icon="list">
    Append extra lines to the summary shown in `202` responses and approval emails — e.g. a gift card discount.
  </Accordion>
  <Accordion title="Webhook delivery" icon="tower-broadcast">
    Hook into outbound webhook dispatch to add logging, custom auth headers, or a secondary delivery target.
  </Accordion>
</AccordionGroup>

<Tip>
  These extension points are still being finalized ahead of release, so exact filter names aren't public yet. [Contact support](mailto:support@cocartapi.com) if you're building an integration and want early details.
</Tip>
