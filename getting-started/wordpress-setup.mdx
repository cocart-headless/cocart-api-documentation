This guide covers how to configure WordPress as an API-only backend for your headless storefront. A headless setup has different requirements than a traditional WordPress site — the frontend is served by a separate application, so WordPress only needs to handle REST API requests and admin access.

## Hosting considerations

In a headless setup, WordPress is an API server. The factors that matter are different from traditional WordPress hosting.

**What matters:**
- **PHP workers** — each API request uses a PHP worker. Concurrent shoppers need concurrent workers. Look for hosting that offers 4+ PHP workers minimum.
- **Object caching** — Redis or Memcached drastically reduces database queries for cart sessions and product data.
- **Low latency** — host your WordPress backend in the same region as your frontend deployment.
- **PHP 7.4+** — required by CoCart, and newer PHP versions are measurably faster.

**What matters less:**
- Page caching plugins (Varnish, WP Super Cache) — your frontend doesn't serve WordPress pages.
- CDN for HTML — your frontend app handles its own CDN. You still want a CDN for WordPress media uploads.
- Theme performance — there's no theme rendering API responses.

### Recommended hosting types

**Managed WordPress hosting** is the easiest option. Providers like Cloudways, SpinupWP, GridPane, or RunCloud handle server configuration, updates, and security. Most include Redis object caching out of the box.

**VPS hosting** (DigitalOcean, Linode, Vultr) gives you full control but requires server management knowledge. A good option if you need custom PHP-FPM tuning or non-standard configurations.

**Shared hosting** works for development and low-traffic stores but will struggle under concurrent API requests due to limited PHP workers and no object caching. Providers like Bluehost, SiteGround, and HostGator offer shared hosting plans.

## wp-config.php configuration

The WordPress configuration file is located at the root of your WordPress installation. These constants optimize WordPress for headless use.

### Site URLs

Define your site URLs as constants to avoid a database query on every request:

```php
define( 'WP_SITEURL', 'https://api.yourstore.com' );
define( 'WP_HOME', 'https://api.yourstore.com' );
```

If WordPress is installed in a subdirectory:

```php
define( 'WP_SITEURL', 'https://yourstore.com/wordpress' );
define( 'WP_HOME', 'https://yourstore.com/wordpress' );
```

[More information](https://developer.wordpress.org/advanced-administration/wordpress/wp-config/#wp-siteurl)

### Memory limit

WooCommerce recommends at least **256M**. For stores with large catalogs or concurrent API traffic, consider 512M:

```php
define( 'WP_MAX_MEMORY_LIMIT', '256M' );
```

[More information](https://developer.wordpress.org/advanced-administration/wordpress/wp-config/#increasing-memory-allocated-to-php)

### Disable WP-Cron

This is one of the most impactful changes for a headless setup. By default, WordPress checks for scheduled tasks on every HTTP request, adding latency to every API call. Disable it and use a system cron instead:

```php
define( 'DISABLE_WP_CRON', true );
```

Then set up a system cron job to run WP-Cron every minute:

```bash
cd /path/to/wordpress && php wp-cron.php > /dev/null 2>&1
```

Or use WP-CLI:

```bash
cd /path/to/wordpress && wp cron event run --due-now > /dev/null 2>&1
```

### Post revisions

Limit post revisions to reduce database bloat. This is less critical for headless but still good practice:

```php
define( 'WP_POST_REVISIONS', 5 );
```

### Disable file edits

Prevent file editing from the WordPress admin. This is a security best practice for any production site:

```php
define( 'DISALLOW_FILE_EDIT', true );
```

### Disable automatic updates

Automatic updates running in the background can cause unexpected downtime. Manage updates manually or through your deployment process:

```php
define( 'AUTOMATIC_UPDATER_DISABLED', true );
```

[More information](https://developer.wordpress.org/advanced-administration/wordpress/wp-config/#disable-plugin-and-theme-update-and-installation)

### Debugging

Enable debug logging during development. Log errors to a file instead of displaying them, since REST API responses should not contain PHP notices:

```php
define( 'WP_DEBUG', true );

if ( defined( 'WP_DEBUG' ) && WP_DEBUG ) {
    define( 'WP_DEBUG_LOG', true );
    define( 'WP_DEBUG_DISPLAY', false );
    @ini_set( 'display_errors', 0 );
}
```

<Warning>
    Disable `WP_DEBUG` on production. Debug output can expose sensitive information in API responses and log files.
</Warning>

[More information](https://developer.wordpress.org/advanced-administration/wordpress/wp-config/#wp-debug)

## Object caching

Object caching stores database query results in memory (Redis or Memcached), so repeated requests don't hit the database. This is critical for headless because:

- Every cart API call reads session data from the database
- Product queries are repeated across requests
- WooCommerce transients are used extensively

Most managed WordPress hosts include Redis. For VPS hosting, install Redis and a WordPress object cache plugin like [Redis Object Cache](https://wordpress.org/plugins/redis-cache/) or use the drop-in provided by your hosting panel.

## Disabling WordPress frontend access

<Info>
    This section is optional but recommended for a true headless experience. It prevents visitors from accessing the WordPress frontend and ensures they interact with your headless storefront instead. Requires **CoCart Starter**.
</Info>

In a headless setup, visitors should be directed to your frontend application, not the WordPress site.

### Using CoCart settings

CoCart's settings allow you to disable WordPress frontend access and redirect visitors to your headless frontend. When enabled:

- Non-admin visitors are redirected to your frontend URL with a **302** redirect
- **Administrators** always retain full access to WordPress
- Cart and checkout pages are pre-populated in the **Accessible Pages** setting — you can add or remove pages from **CoCart → Settings**
- **HEAD requests** pass through so your headless frontend can detect redirects

### Using filters

For more control, use CoCart's filters in a custom plugin or your theme's `functions.php`.

<Note>
  Filters take precedence over whatever is configured in **CoCart → Settings**.
</Note>

**Disable WordPress access:**

```php
<?php
// Disable WordPress frontend for non-admins
add_filter( 'cocart_wp_disable_access', function() {
    return 'yes';
});
```

**Set the frontend redirect URL:**

```php
<?php
// Redirect visitors to the headless frontend
add_filter( 'cocart_wp_frontend_url', function() {
    return 'https://store.yourfrontend.com';
});
```

**Control which pages remain accessible:**

By default, the WooCommerce cart and checkout pages are still accessible even when WordPress is disabled. You can customize this:

```php Only allow the checkout page
<?php
add_filter( 'cocart_wp_accessible_page_ids', function( $page_ids ) {
    $checkout_id = get_option( 'woocommerce_checkout_page_id' );

    return array( $checkout_id );
});
```

```php Block all WordPress pages (admin-only access)
<?php
add_filter( 'cocart_wp_accessible_page_ids', function() {
    return array();
});
```

## Setting up CORS

When your frontend application is on a different domain than WordPress, browsers block cross-origin API requests by default. CoCart includes built-in CORS handling.

Enable CoCart's CORS support:

```php
<?php
add_filter( 'cocart_disable_all_cors', function() {
    return false;
});
```

Restrict to your frontend domain:

```php
<?php
add_filter( 'cocart_allow_origin', function() {
    return 'https://store.yourfrontend.com';
});
```

<Warning>
    Never use a wildcard (`*`) for `Access-Control-Allow-Origin` in production. Always specify your frontend domain.
</Warning>

For full CORS configuration details, see the [CORS documentation](/cors).

## Reducing unnecessary load

A headless WordPress site doesn't need everything a traditional site loads. Consider:

- **Deactivate frontend-only plugins** — SEO plugins, page builders, form plugins, and caching plugins that only affect HTML output.
- **Use a minimal theme** — activate a lightweight theme (or a blank theme) since it's never rendered for visitors.
- **Disable embeds and emoji scripts** — WordPress loads these on every page by default, including REST API requests in some configurations.

## Summary

A minimal headless `wp-config.php` setup:

```php
// Site URLs (avoids DB query per request)
define( 'WP_SITEURL', 'https://api.yourstore.com' );
define( 'WP_HOME', 'https://api.yourstore.com' );

// Performance
define( 'WP_MAX_MEMORY_LIMIT', '256M' );
define( 'DISABLE_WP_CRON', true );
define( 'WP_POST_REVISIONS', 5 );

// Security
define( 'DISALLOW_FILE_EDIT', true );
define( 'AUTOMATIC_UPDATER_DISABLED', true );

// Debugging (disable on production)
define( 'WP_DEBUG', false );
```
